COMPLETE — H20 two-TP4 full-model crossover for vLLM PR #61088

The cold 16K/c4 cell has a positive signal in both placements (+3.81% and +2.45%; pooled median +2.29%). The predeclared cold 16K/c16 primary is effectively unchanged, and warm 16K/c16 is slightly lower. Other low-concurrency cells change direction after the GPU swap. These measurements do not establish a stable general model speedup; keep the PR as Draft.

Configuration and method
Baseline: vLLM 1ee69dde9 plus the common, existing #60613 sentinel correctness fix. Candidate: the same image with only PR #61088 runtime files at 4fe427bd137145c3cd9a8a12c0517d53b533976f. Original and candidate source hashes are in analysis-summary.json. No weights, precision, backend configuration or sampling settings were changed.
Full DeepSeek-V4.1-Flash weights; H20-3e / SM90; torch 2.13.0+cu130; TP4, DP1, EP, MRV2, Humming, Engram CPU offload, APC enabled, 16K token chunk and real DSpark 5 standard rejection. No synthetic acceptance. The two instances use disjoint four-GPU groups, disjoint sets of 44 CPU IDs, and separate NUMA allocations. Only one instance receives requests at a time; the peer's request/token/draft counters are checked unchanged.
Two complete engine startup pairs, with physical GPU groups swapped for the second pair. Each of six workloads has two excluded calibration pairs and three measured pairs per placement. Orders are AB/BA/AB in phase0 and reversed in phase1. This is six measured batches per arm/cell, not six independent model restarts. All 72 measured batches and 48 calibration batches completed. The measured batches contain 1,152 requests and 1,179,648 generated tokens.
Inputs are fixed synthetic ledger prompts, 4,096 or 16,384 tokens. Every request generates exactly 1,024 tokens (temperature 0, top_p 1, seed 713, ignore_eos true). Each batch contains twice the concurrency in requests, with continuous refill workers. Output tok/s includes full HTTP request processing and the final request drain; it is not pure prefill throughput or a permanently saturated steady-state measurement.
Cold: reset APC before each batch and assert cached_tokens == 0 for every request. Warm: two untimed priming passes and exact per-request verification against observed hits. Warm 16K hits 99.609375%; warm 4K hits 98.4375%. Both retain 64 residual prompt tokens; neither is literal 100% hit.

Interpretation
Cold 16K/c4 is worth retaining as a positive signal, but it is not sufficient to claim a stable code-derived gain. Its per-batch variation exceeds the pooled change, and candidate acceptance is also higher in both placements. Throughput and acceptance are jointly affected by generated text, batching and request drain. Do not divide by acceptance to manufacture an adjusted model gain, discard the unfavorable third pair, or fit dispatch to a benchmark context/concurrency boundary.
The unchanged baseline also produces different long-text hashes across repeats. Phase0 acceptance/throughput correlations are high, but these are descriptive associations, not proof of causality or proof that fusion cannot affect outputs. The exact-byte operator checks and the separate quality subset are the relevant correctness evidence.
Only four compressed-KV producers per rank use this fusion: C2 at layers 2/8/14 and C1 at layer 20. Source inspection shows the split path overlaps main-cache insertion with indexer preparation, while the fused path finishes the combined operation before indexer preparation. That can limit the end-to-end value of a faster isolated chain; no NCU-derived causal claim is made.

Correctness and memory
Carried-forward validation on identical PR source: 46 targeted GPU pytest cases passed, plus 18 exact-byte state/latent/cache stress cases including CUDA Graph replay. Device-batched operator measurements covered 26 shapes and found 1.18–1.53x isolated speedup. These are operator results, not model gains.
The earlier fixed 128-question GSM8K subset, five-shot with natural EOS and max 1024 tokens, scored 123/128 baseline and 124/128 candidate using the final-number extractor frozen before B. Each arm parsed 125 answers; 122 numeric answers matched and 46 full messages matched. No answer was truncated. This is a regression subset, not full-model quality evaluation or evidence of improved accuracy.
All four ranks, both placements: after-load PyTorch allocated 79,796,461,056 bytes and reserved 80,065,069,056 bytes in both arms. Fresh readiness snapshots: A 119,175 MiB per GPU; B 119,177 MiB per GPU (+2 MiB). These snapshots are not peak VRAM. There is no additional persistent weight representation.

Run integrity and cleanup
The first dual-r1 attempt failed before any benchmark samples because the metadata comparison did not normalize the GPU- prefix omitted by torch's UUID string. It was archived separately. Only metadata normalization changed in r2.
During phase0, the launcher session reported the bastion idle disconnect and the original controller was later absent. The independent phase0 benchmark client completed all six workloads with exit code 0. A detached recovery controller verified the completed phase, stopped only its exact owned containers and resumed only phase1. The original plan, code, sample counts and absolute time bound were retained; no measured samples were removed or repeated.
All six owned containers (four models and two CPU clients) stopped with exit code 0. active.json is absent, and a fresh final check found all eight selected H20 GPUs at 0 MiB / 0%, with no compute processes. The existing unrelated container was not changed. Original images and read-only weights were not modified; candidate source changes were confined to owned container layers.
NCU counter access and human line review remain pending. No host settings or container capabilities were changed. Other SM90 products have not been benchmarked.
